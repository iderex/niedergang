# 0026. What the default suite may need

## Date

2026-08-08

## Status

accepted

## Question

What may a test in the default suite depend on, and what happens to a test that
needs more than that.

The question is asked before there is a suite because the answer is a birth
requirement. A suite acquires its dependencies one test at
a time, each one defensible on the day it lands, and the point at which the
whole is no longer runnable is not a point anybody decides.

What this record does not answer is where the tests that need more than this go.
That is issue #30, which names each separated suite for what it needs. This
record fixes what the default suite may not need, and issue #29 is where the
check that holds it lives.

## Options considered

No rule, with each test judged on its merits when it is written. This is the
state a project is in unless it says otherwise, and it is not neutral. Every
individual dependency arrives with a reason, and the suite stops being runnable
by accumulation, and no decision was taken.

A rule written down and left to review. Cheap, and it holds exactly as long as
whoever reviews remembers to look. The failure is silent in both directions: a
test that reaches the network passes on a machine that has one, and the reviewer
who would have caught it sees a green run.

A rule with a mechanism on the test side, so that a default-suite test which
binds off loopback or opens a connection is refused and never trusted not to.
This costs an interception surface that has to exist in the language and a
fixture that proves the guard bites. Taken below, with the mechanism owed to
issue #29.

An environment-level rule instead, with the default suite run inside a sandbox
that has no network and no display. Attractive because it needs no cooperation
from the test, and it fails on where the suite is run. A contributor runs the
suite on their own machine, which has both, so the property would hold on the
gate and not where the defect is written. It is a useful second layer and it is
not the rule.

On a test that genuinely needs elevation.

Grant it, by having the suite acquire the privilege it needs. This is the option
that has to be written down in order to be visibly rejected. It puts a
consent prompt in front of whoever is sitting at the machine, and on a managed
workstation it makes the suite unrunnable by the person most likely to be
running it.

Work around it, by finding the unprivileged path that achieves something close
to the same thing. Worse than granting it, because the test then passes while
covering something other than what it names, and nothing in the output says so.

Skip it and disclose the skip. Taken below.

## Decision

A test in the default suite runs without a display, without a privileged
account, without the network, and without anything on the machine that the
repository did not put there.

Concretely, and the list is the decision itself, in the
same sense record 0010's refusal list is:

A default-suite test opens no window. Anything that draws renders to a file and
the test compares the file.

A default-suite test needs no privileged account, no elevation and no consent
prompt.

A default-suite test binds no socket off loopback and opens no outbound
connection. Loopback is permitted because a test of the tool's own command
surface talking to its own process is not a network dependency.

A default-suite test writes only inside a temporary directory it created and
removes, and nothing under the source tree or the user's own directories.

A default-suite test reads no data set that is not tracked in this repository or
generated by the test itself. A fixture fetched at test time is a network
dependency wearing a different word.

A default-suite test needs no hardware beyond a processor and memory.

A test that needs any of those is not weakened until it fits. It moves to the
suite of issue #30 named for what it needs, and that suite is invoked
deliberately.

On elevation specifically, because it is the one where the wrong answer looks
like diligence. A test that cannot run without a privileged account is skipped,
and the skip is disclosed in the run's own output naming the test and what it
would have needed. It is never worked around, and the disclosure never turns
into a claim that the suite covered it. Two spellings of the workaround are
named here so that neither reads as an oversight later: acquiring the privilege
inside the suite, and substituting an unprivileged path that exercises something
adjacent while keeping the original name.

The hardware category exists and is empty. This project has no instrument in its
path today and none is invented to look thorough. If a graphics processor is
ever used to run samples, that path gets a suite named for the hardware and the
documentation says plainly that the default gate does not cover it.

What a run says about itself is the other half of the rule and it is not
optional. A run that covered less than everything may not read as one that
covered everything and found nothing, so the default run names every suite,
says whether it ran, and says what running the others would cost. Where that is
enforced is issue #29 and not here; this record is where the obligation is
stated.

The mechanism for the loopback and network clauses is a guard on the test side,
because the property has to hold where a contributor runs the suite and not only
on the gate. What such a guard can intercept in Rust is not settled here and no
design is asserted: record 0002 fixes the language, and what the test harness
and the socket API make interceptable is a question for whoever writes issue
#29. It is stated as an obligation with a named owner, and until a fixture
reddens on a test that binds off loopback, the clause is read by a person.

## Reasons

A suite that needs a display or a password is a suite that stops being run, and
a gate nobody runs means nothing while continuing to look like a gate. The cost
of that is not the missing coverage. It is the green check standing for a
property nothing tested, which is the failure this board is trying to keep out
of the physics and which is cheaper to prevent in the tooling.

The elevation clause is not only about a pipeline. On a developer machine a
socket bound off loopback raises a firewall dialog that only an administrator
can answer, and a test that wants a certificate in a trust store raises a
consent prompt. Both interrupt whoever is sitting at that machine, and the
person interrupted is usually not the person who ran the suite.

The rule is stated as what the default suite may not need and not as what it
may, because the second form is a list that has to be extended every time a
legitimate dependency appears, and a list that has to be extended is one that
gets extended without argument.

Naming the separated suites for what they need, where calling them integration
was open, is the same reasoning one level up. A reader of a green default run
can tell what was not covered only if the uncovered thing has a name that says
what it is.

## Reasons against

The strongest argument against this record is that it makes some genuinely
valuable tests expensive. A test against a real space weather file from the real
service is a better test than one against a tracked fixture, and this rule puts
it in a suite that does not run on a pull request. The answer here is that the
tracked fixture tests the tool and the network test tests somebody else's
server, and only the first belongs on a gate, but that answer is an argument and
it is worth knowing it is one.

The second is that the guard is owed. A rule whose
mechanism is another issue is a rule that holds by memory in the window between
the two, and this project's own position is that a sentence in a document is an
explanation of a rule and not a rule. That window is real and it is open now.

The third is the loopback exception. It is a judgement about where a boundary
sits, and a test that binds loopback and then talks to
something that is not the tool would satisfy the clause while defeating it. No
mechanism distinguishes the two, and none is proposed.

The fourth is that a skipped test is a test that does not run, and a project
with a disclosed skip and a project with no test at all differ by a sentence.
The difference is real, because the sentence is what a reader can act on, and it
is smaller than it sounds.

## What would change this

A test that genuinely cannot be written under this rule and whose absence costs
more than the rule protects. It would arrive as a specific test, and the answer
might be a fourth separated suite, leaving this record unchanged.

A measurement showing that the default suite has become slow enough that a
contributor stops running it locally, which would move the boundary between the
default suite and the long-running suite of issue #30 and would not remove it.
Nothing has been measured, because there is no suite:

    git ls-tree -r --name-only origin/main | grep -c -E 'Cargo\.toml|\.rs$|rust-toolchain'
    0

run at `39ed198ce3278045bff1d9fc4a0752d7b5435af9`.

A finding from issue #29 that the test-side guard this record asks for cannot be
built in Rust in a form that refuses, leaving one that only reports. That would
not change the rule, and it would change what this record may claim about it:
the clause would be marked as read by a person, with the reason, and would stop
reading as enforced.

An instrument entering this project's path, which would give the empty hardware
category a member and require the documentation to say what the default gate
does not cover.

## What depends on this

Issue #29, the test gate, which owns both the check that runs this suite and the
guard that makes this record enforcement, and which
also owns the run's statement of which suites ran and which did not.

Issue #30, the separated suites, which is where every test excluded here goes
and which names each suite for what it needs.

Issue #33, the coverage check, whose figure is derived from the default suite
only. A refusal path reachable only from a separated suite is permanently
uncovered by that measure, and whether it is reported as uncovered or excluded
with a reason is decided there and not here.

Issue #45, the propagation regression set, and every later regression set, each
of which states that it runs inside the default gate and therefore inherits this
list.

Record 0012, whose byte-identical property is checked by running a case more
than once at different thread counts. That check needs no network, no display
and no elevation, so it belongs in the default suite by this record, and it is
also the most likely candidate to become slow enough to argue about.
